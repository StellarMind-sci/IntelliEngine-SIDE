# 项目开发流程说明

本文描述 IntelliEngine-SIDE 从产品意图到生产发布的完整开发路线。它是流程事实，
不记录实时任务状态；实时状态只存在于 GitHub Issues、GitHub Project 和 Pull Request。

## 一、长期事实与状态来源

| 信息 | 唯一事实来源 |
| --- | --- |
| 产品目标、术语、非目标 | `docs/product/` |
| 当前系统架构与公共契约 | `docs/architecture/`、已接受 ADR、接口定义和测试 |
| 待讨论设计 | `docs/rfc/` |
| 已接受架构决定 | `docs/adr/` |
| 里程碑顺序 | `docs/roadmap/milestones.md` |
| 已完成的大阶段 | `docs/roadmap/stage-log.md` |
| 实时任务、依赖和阻塞 | GitHub Issues 与 GitHub Project |
| 实现、审查与合并证据 | Git 分支、Pull Request、CI 和测试报告 |
| 临时探索 | Codex 对话；不得作为长期事实 |

出现冲突时，以代码和测试、已接受 ADR、当前公共契约和仓库规则为准；未接受 RFC
不能覆盖已接受 ADR。

## 二、从想法到交付的主流程

```text
产品愿景或问题
  → Epic / 里程碑目标
  → 必要时编写 RFC
  → 产品负责人作出决定
  → 建立或更新 ADR
  → 拆成可合并的 GitHub Issues
  → 公共契约与契约测试先行
  → 模块在独立 worktree 中实现
  → 独立审查
  → 跨模块集成与端到端验证
  → Pull Request 合并 main
  → staging 验证
  → 人工批准 production
  → 达到退出条件后记录阶段日志
```

### 1. 产品和架构规划

1. 先核对愿景、术语、非目标、当前架构和里程碑。
2. 只影响单模块内部且不改变公共契约的决定，可以直接进入 Issue。
3. 影响多个模块、公共契约、持久化、权限、溯源或部署的决定，必须先写 RFC。
4. RFC 必须列出目标、非目标、接口、数据流、替代方案、兼容性、安全、测试、发布、
   回滚以及待产品负责人决定的事项。
5. RFC 只有在产品负责人明确接受后，才能转化为 ADR；未接受前不得开始依赖它的并行实现。

### 2. 将决定拆成 Issue

每个 Issue 都是一个 Codex 任务契约，至少包含：

- 背景和一句话交付结果；
- 范围、非目标、主要模块和允许修改路径；
- 输入、输出和公共接口影响；
- 依赖的 RFC、ADR、契约和其他 Issue；
- 可验证的验收条件与必须运行的测试；
- 风险、兼容要求和回滚方式。

如果一个任务跨多个主要模块、包含两项以上公共接口变化、无法由一个 PR 交付，或无法由
一组独立测试验收，就必须继续拆分。

### 3. 契约优先

1. 公共契约先形成 RFC/ADR，再实现 schema、类型、校验器和语言无关测试向量。
2. 契约变更必须通过独立契约审查。
3. 契约及契约测试合并后，使用方才能并行开发。
4. 未知版本、未知类型、序列化、迁移、错误码、权限和溯源都属于契约的一部分。
5. 不允许多个任务同时修改同一个尚未稳定的契约。

### 4. 单 Issue 实现

1. 从最新的受保护基线创建一个分支和一个独立 worktree。
2. 新 Codex 任务只加载 Issue、适用的 `AGENTS.md`、直接相关接口、少量 ADR/RFC 和测试失败信息。
3. 修改前核对允许路径、非目标、依赖和验收条件。
4. 采用最小完整实现；发现范围扩大时停止，并回到中央会话拆分 Issue。
5. 运行模块测试、受影响契约测试、必要的集成与安全测试。
6. 交接必须报告修改文件、命令和结果、接口变化、剩余风险、回滚方式和未完成事项。

### 5. 独立审查和修正

实现任务不能自行成为最终审查者。另一个 Codex 任务检查：

- 是否满足 Issue，而没有隐性扩展范围；
- 公共接口、兼容性、权限、溯源和回滚是否完整；
- 测试是否真实覆盖验收条件；
- 文档、代码、schema 和测试之间是否发生漂移。

审查结论分为 `通过`、`修改后通过`、`阻断`。修正应回到原实现任务；若修正要求扩大
契约或路径，则创建新的 Issue，不在原 PR 中追加。

### 6. 集成、合并和发布

1. 跨模块联调使用独立集成 Issue 和 worktree。
2. PR 依次通过格式/Lint、类型检查、单元测试、契约测试、集成测试、安全测试、兼容测试和构建。
3. PR 由产品负责人或指定维护者批准后才能合并 `main`。
4. `main` 自动进入 staging；生产发布必须使用版本标签并经人工批准。
5. 高风险功能使用 feature flag；数据变更必须提供向前迁移、兼容期和回滚方案。
6. 只有整个里程碑满足退出条件并完成验收后，才更新阶段日志。

## 三、里程碑推进路线

- M0 治理底座：仓库、规则、模板、CI、GitHub 治理和 Codex skills 可用。
- M1 公共契约：公共类型、schema、校验器和契约测试稳定，可以支持模块独立开发。
- M2 数学垂直切片：输入到工程包导出的第一条端到端链路通过验收。
- M3 视频转工程：合法内容的捕获、时间溯源、知识/项目/Agent 萃取链路通过验收。
- M4 及以后：扩展输入、学科、本地运行时、外部工程工具和真人协作。

详细范围以 `docs/roadmap/milestones.md` 为准。不得为了展示进度跳过契约门禁或阶段退出条件。

## 四、并行与串行规则

可以并行：模块边界独立、依赖契约已经合并、不会修改同一核心文件或数据结构的 Issues。

必须串行：RFC 与其审查、契约与使用方、数据库 schema 变更、同一核心文件、高冲突模块、
同一发布门禁。中央会话负责维护依赖顺序，不让子任务自行启动下游工作。

## 五、阶段退出与记录

一个大阶段只有同时满足以下条件才算完成：

1. 该阶段定义的交付物全部合并到权威分支；
2. 必需 CI、契约、集成、安全和回归测试通过；
3. 阻断级问题已关闭，剩余风险已被明确接受；
4. 当前架构、ADR、运行手册和回滚说明已同步；
5. 产品负责人明确验收。

满足后，在 `docs/roadmap/stage-log.md` 追加一条不可覆盖的完成记录。

## 六、异常处理

- 范围扩大：停止实现，创建或修改 Issue。
- 契约冲突：停止使用方开发，先处理 RFC/ADR 和契约审查。
- 测试失败：保留失败证据，不得用删除测试或弱化断言伪造通过。
- 上下文压缩或中央会话更换：按 `docs/runbooks/codex-development-guide.md` 执行记忆重载。
- 发布失败：按 `docs/runbooks/rollback.md` 回滚，并在 Issue/PR 保留证据。

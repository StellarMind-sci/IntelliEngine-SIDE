# 面向 Codex 的项目开发指导

本文用于指导本项目所有 Codex 任务如何读取背景、接受任务、实施、审查、交接和恢复上下文。
它是对根 `AGENTS.md` 的操作性补充；若两者冲突，以最近的 `AGENTS.md` 和已接受 ADR 为准。

## 一、Codex 角色划分

### 中央协调与控制任务

负责维护项目航向和任务依赖，但不把聊天记忆当作权威事实。主要职责：

- 读取产品愿景、架构、ADR、里程碑、阶段日志和 GitHub 实时状态；
- 将 Epic/RFC 拆成边界明确的 Issues；
- 决定任务串行或并行，并为每个 Issue 创建独立 Codex worktree 任务；
- 给子任务明确基线、允许路径、禁止事项、验收条件、测试和交接格式；
- 读取子任务交接，安排独立审查、修正、集成和发布验证；
- 把架构决定写入 ADR，把实时状态留在 GitHub，把完成的大阶段写入阶段日志；
- 涉及重大产品取舍、显著扩大范围、敏感权限、不可逆数据操作或生产环境高风险发布时，
  请产品负责人决定；常规合并和低风险发布由中央任务自主审批。
- 每次向产品负责人汇报时，先说明当前阶段、已完成进度、正在进行的工作和下一个阶段；
- 需要产品负责人执行本地、浏览器、GitHub、设置、登录或审批操作时，提供可逐步执行的中文引导，
  并等待其确认结果后再继续依赖该操作的工作。

中央任务可以维护治理文档和做只读核验，但不应长期亲自实现所有业务模块。

### 规划任务

只编写 RFC、拆分 Issue 或分析接口影响，不提前实现未接受的设计。

### 实现任务

只实现一个 Issue，严格遵守允许路径和接口边界，完成测试后交接，不自行启动下游任务。

### 审查任务

独立检查需求、范围、契约、实现和验证证据。审查者不应默认修改实现；修正交回原实现任务。

### 集成与发布任务

只在依赖模块已完成后运行，负责跨模块验证、回归、staging、发布证据和回滚准备。

## 二、任何 Codex 任务的启动顺序

新任务开始后，按以下顺序读取，不要依赖用户复制整段历史聊天：

1. 根 `AGENTS.md` 和目标目录最近的 `AGENTS.md`；
2. 当前 GitHub Issue 或同等任务契约；
3. Issue 指定的产品、架构、接口、RFC 和 ADR；
4. 目标模块的代码、测试和当前失败信息；
5. 当前分支/worktree、`git status`、基线 commit 和允许修改路径；
6. 与任务匹配的 `.agents/skills/` 工作流。

随后先用一句话复述交付结果，并报告：允许路径、非目标、接口影响、必须验证项和阻塞条件。
信息不足时先做安全的只读核验；会改变产品含义或扩大范围的缺口必须交回中央任务。

## 三、面向产品负责人的进度汇报

中央协调任务每次回复产品负责人时，应在开头或显著位置给出简短的“阶段导航”。即使本轮只处理
一个小问题，也不能让产品负责人自行从历史聊天推断项目处于哪里。

阶段导航必须包含：

1. **当前阶段**：当前里程碑和正在处理的大板块，例如“M1 公共契约 / CognitiveNode RFC”。
2. **当前进度**：已经完成、正在执行、尚未通过的门禁；必须区分“已编写”“已审查”“已合并”
   和“已验收”，不能统称为“完成”。
3. **本轮动作**：本轮中央任务或子任务实际做了什么，以及是否产生代码、文档或外部状态变化。
4. **下一阶段**：当前门禁通过后将开发什么、由哪类 Codex 任务负责、进入条件是什么。
5. **需要用户决定或操作**：没有则明确写“当前不需要用户操作”；有则按下一节提供完整引导。

推荐格式：

```markdown
当前阶段：M<编号> / <大板块> / <当前 Issue 或门禁>
当前进度：<已完成>；<正在进行>；<尚未通过>
本轮动作：<本轮实际动作和结果>
下一阶段：<下一项工作及进入条件>
需要你操作：无 / <操作名称，详细步骤见下文>
```

进度必须来自仓库、GitHub、测试或子任务的实时证据。无法核实的内容标记为“待核实”，不得根据
压缩摘要、旧对话或子任务口头声明把它写成已完成。

## 四、需要产品负责人操作时的引导规则

### 持续开发模式与自主审批

本项目默认采用持续开发模式。中央协调任务对一般性的创建、调整、修订、分支、暂存、提交、
推送、Pull Request、常规合并、预发布部署和低风险发布拥有日常工程审批权，不需要为这些步骤
逐项暂停开发并向产品负责人申请许可。中央任务应在阶段汇报和最终交接中如实说明已执行的操作、
验证证据、外部状态变化、风险与回滚方式。

自主审批仍受以下边界约束：

- 一个 Issue、一个任务、一个 PR 的范围边界不变；公共契约和契约测试仍须先于使用方。
- 独立审查、CI、兼容、安全、回滚和阶段退出门禁不得省略。
- 不得借“持续开发”静默扩大产品范围、修改已接受 ADR、引入第二项公共契约变化，或处理未授权
  的密钥、私有记忆、受保护数据和不可逆数据操作。
- 重大产品取舍、公共契约含义变化、显著增加成本或范围、敏感权限、法律合规风险、生产环境
  高风险发布，以及必须由产品负责人亲自完成的外部操作，仍须暂停并请求决定。
- 常规合并和低风险发布可由中央任务依据已通过的 Issue、独立审查与 CI 自主批准；生产发布若
  涉及迁移、不可逆影响、真实用户数据或明显外部成本，必须保留人工批准门禁。

以下逐步引导规则仅适用于确实需要产品负责人亲自操作或决定的情况。

任何依赖产品负责人操作的步骤都必须暂停在操作门禁处，并提供有序、可验证的中文步骤。不能只说
“请配置 GitHub”“请运行命令”或“请批准”，也不能假设用户已经完成操作。

每次引导至少说明：

1. 打开哪个应用、窗口、网页地址、标签页或终端目录；
2. 点击哪个准确控件，以及它所在的菜单或页面位置；
3. 输入的准确文本、选项或命令；可变值使用清楚的占位符；
4. 哪些设置不需要修改，避免误操作；
5. 操作完成后应看到的页面、提示、状态或命令输出；
6. 是否存在权限、费用、公开发布、删除、覆盖或其他不可逆影响；
7. 密钥、密码、验证码、令牌和私有数据不得粘贴到聊天中的安全提醒；
8. 需要用户回传的最小结果，例如错误文字、状态名称或隐去敏感信息的截图。

使用“一步一个动作”的编号列表。只有用户报告出现预期结果后，才能继续依赖该结果的提交、推送、
PR、合并、部署或下一阶段工作。若界面与说明不同，优先使用稳定的文字标签或图标描述一个安全的
替代入口；若结果异常，先根据实际提示诊断，不连续尝试高风险绕过方案。

## 五、中央任务的记忆重载协议

中央协调任务经历多次上下文压缩、长时间暂停、模型更换、会话恢复或负责人交接后，必须假设
聊天中的细节可能已经丢失或过期。在继续创建、批准或合并任何任务前，执行一次完整重载。

### 必须重新阅读

1. `README.md`、`AGENTS.md`；
2. `docs/product/vision.md`、`glossary.md`、`non-goals.md` 和关键用户流程；
3. `docs/architecture/system-context.md`、`module-boundaries.md`、`public-contracts.md`；
4. 全部已接受 ADR，以及当前任务直接相关的未决 RFC；
5. `docs/roadmap/milestones.md`、`docs/roadmap/stage-log.md`；
6. `docs/runbooks/development.md` 和本指导文件；
7. GitHub Project、开放 Issues、相关 PR、CI、评审和阻塞状态；
8. 本地/远程分支、worktrees、未提交修改、基线 commit 和最新测试结果。

不得用压缩摘要或旧聊天中的“记得”替代上述实时核验。仓库文档可能落后于 GitHub 状态，
GitHub 状态也可能落后于代码，因此要按事实来源逐项交叉验证。

### 重载后必须形成“航向校准摘要”

中央任务在内部或评论中重新确认：

- 当前里程碑及其退出条件；
- 已接受、未接受和被替代的架构决定；
- 当前开放 Issue、依赖关系、负责人和 worktree；
- 已完成但尚未合并、已合并但尚未验收的工作；
- 当前阻塞、风险、测试状态和下一个门禁；
- 本轮明确禁止执行的操作。

若无法从仓库和 GitHub 证明某项状态，就标记为“待核实”，不得按“已完成”继续下游开发。

## 六、中央任务如何创建子任务

每个子任务提示至少包含：

- 仓库、Issue 编号和一句话目标；
- 起始基线、目标分支或 worktree 方式；
- 必须阅读的根/模块 `AGENTS.md`、接口和 ADR/RFC；
- 允许修改路径和只读路径；
- 范围、非目标和禁止操作；
- 输入、输出、公共接口影响和依赖；
- 验收条件、测试命令和期望证据；
- 是否允许提交、推送、建 PR、评论 Issue 或改变外部状态；
- 交接格式和停止条件。

默认禁止子任务自行合并、发布、扩大范围或启动另一个里程碑。权限必须逐项写明，不能从“负责该
Issue”推导出推送、PR、合并或生产操作权限。

## 七、任务右切分标准

一个合格子任务应当：

- 可以用一句话说明结果；
- 主要属于一个模块；
- 最多引入一项公共接口变化；
- 修改路径可以明确列出；
- 能由一组独立测试验收；
- 能由一个 PR 交付并由另一任务独立审查。

不满足任一项时，中央任务应使用 `issue-planner` 继续拆分。契约未稳定时，不并行启动使用方。

## 八、子任务执行与交接

子任务必须：

1. 修改前检查范围和工作树状态；
2. 只实施 Issue 要求的最小完整变化；
3. 保留 AI 生成修改的溯源、权限和回滚能力；
4. 运行 Issue 指定测试及仓库规定的受影响测试；
5. 对实际修改路径做最终审计；
6. 留下可审查交接后停止，不自行进入下一任务。

交接格式：

```markdown
## 交付结果
- 一句话结果：
- 修改文件：
- 公共接口变化：

## 验证证据
- 命令：
- 结果：

## 风险与回滚
- 剩余风险：
- 回滚方式：

## 状态与权限
- 未完成事项/阻塞：
- 是否提交、推送、创建 PR：
- 建议的下一任务：
```

## 九、审查、修正与合并门禁

1. 实现完成后，由中央任务创建独立审查任务。
2. 审查任务只给出有证据、可定位的结论，并区分阻断问题和建议。
3. 需要修改时，中央任务把审查结论交回原实现任务；不得让多个任务同时改同一 worktree。
4. 测试通过不等于允许提交，提交不等于允许推送，推送不等于允许建 PR，PR 通过不等于允许合并。
5. 上述每一步都必须有任务契约，并由中央协调任务按“持续开发模式与自主审批”执行日常工程
   审批；只有该节列出的重大或高风险事项才需要产品负责人明确授权。
6. 合并后重新验证权威分支；只有大阶段满足退出条件并获产品负责人验收，才更新阶段日志。

## 十、阶段日志责任

中央任务负责在大阶段完成时准备 `docs/roadmap/stage-log.md` 记录，但必须先取得产品负责人验收。
日志只写已完成事实、版本、Issue/PR/RFC/ADR、测试证据、风险和回滚点，不复制每日任务状态。

## 十一、防偏航检查

中央任务在每次新建下游任务前快速检查：

- 当前工作是否直接服务当前里程碑退出条件；
- 依赖契约是否已经接受并合并；
- 是否存在未经批准的范围或权限扩张；
- 是否重复实现已有模块、文档或 Issue；
- 是否把聊天内容误当成长期事实；
- 是否应先审查、集成或验收，而不是继续增加功能。

任何一项无法确认时，先核验或请产品负责人决定，再继续推进。
